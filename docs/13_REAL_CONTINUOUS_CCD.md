## Candidate generation versus collision events

Within a single *linear* simulation timestep, a vertex follows

    x(t) = (1-t) x0 + t x1,   0 <= t <= 1.

Its complete trajectory lies in the endpoint AABB. For a moving edge or
triangle, the envelope enclosing all incident swept vertex AABBs is
conservative. But overlapping boxes tell us only that an interaction
is *possible*, not that both features touch at the SAME time.

A moving vertex p and moving face (a,b,c) actually touch if there
exist t, u, v with 0<=t<=1 and u,v>=0 and u+v<=1 such that

    p(t) = (1-u-v) a(t) + u b(t) + v c(t).

Two moving segments (a,b) and (c,d) touch if, for some t,u,v
in [0,1],

    a(t) + u[b(t)-a(t)] = c(t) + v[d(t)-c(t)].

The official IPC Toolkit implements robust numerical CCD for these
moving feature stencils. These continuous events are not captured
by checking just t=0 and t=1 and cannot be inferred from AABB overlap.

## What the Stage-4 source actually checks

The C++23 test at tests/ipc_continuous_ccd_tests.cpp links the
ACTUAL upstream IPC Toolkit v1.6.1 (pinned to commit
19bcab7e1f5a0d2addfcd28513422ff248ea504e).

For every scene:
1. Build a real official ipc::LBVH from start/end vertex positions
   and original topology; obtain VF and EE feature candidates.
2. Call the official FaceVertexCandidate::ccd and
   EdgeEdgeCandidate::ccd routines on all candidate stencils.
3. Independently enumerate *all admissible* VF and EE feature
   stencils, without using LBVH, and run the SAME upstream CCD.
4. Fail if the entire detected-event sets differ even by one pair.

This is independent **feature enumeration**, not independently
developed CCD mathematics. Analytically constructed scenes
independently test whether genuine events are found.

There are 7 controlled analytical scenarios and 28 seeded
randomized 3D linear-motion scenes, for 35 cases total.

## Analytic cases and proof

A fixed triangular face with vertices (0,0,0), (1,0,0),
(0,1,0) lies in z=0. A vertex moves from (0.2,0.2,1)
to (0.2,0.2,-1). Its endpoints are nonintersecting,
but its position at t=.5 lies strictly within the triangle:
z(.5)=0 and x+y=.4<1. Hence genuine mid-step VF contact exists.

An asymmetric crossing from z=1 to z=-1.5 has exact contact
t=1/2.5=.4. The upstream CCD may report a conservative
earlier safe step than the exact mathematical instant.

A vertex at (0.8,0.8,z), z=1 to -1, crosses the
INFINITE plane at t=.5 but x+y=1.6>1. Its swept
AABB overlaps that of the triangle, yet there is NO
actual vertex-triangle collision. This deliberately
tests rejecting a broad-phase false positive.

A non-crossing vertex from z=1 to z=2 stays separate.

For edge-edge, a stationary edge along X from (-1,0,0)
to (1,0,0) and a moving edge along Y from
(0,-1,z) to (0,1,z), z=1 to -1, intersect at
(0,0,0) at t=.5. Their endpoint geometries are
separated. Other edge fixtures are separated or
have overlapping swept boxes only because they occupy
the same spatial regions at DIFFERENT times.

The 28 random scenes do NOT have independent
analytical event-time labels. They are useful for
all-pairs enumeration coverage, not independently
certified numerical CCD correctness.

## Correct numerical interpretation

The official CCD's reported time-of-impact may be a
CONSERVATIVE fraction just before the exact contact,
not necessarily equal to the mathematical contact time.
The test therefore requires a safe, bounded fraction
consistent with the analytic construction, not exact
floating-point equality.

The C++ gate covers *linear* paths only. Stage-1 cubic
Bezier envelopes can conservatively generate candidates,
but passing nonlinear endpoints straight into the linear
IPC narrow phase would be unsound. General nonlinear CCD
needs a separately justified narrow-phase solution or
solver-approved linear substeps.

This gate does NOT implement a physical solver, contact
impulses, friction, nonlinearly moving mesh CCD, total
solver benchmark, SCA maintained frontier or new claimed
algorithmic performance.

## Native evidence and visualization

The test writes original signed-off source measurements:

- ccd_cases.csv: 35 scenarios, actual LBVH candidate counts,
  official narrow-phase events, independent enumerated CCD
  events, TOIs, and paid timing for each phase.
- linear_vertex_paths.csv: 121 analytical path samples
  for selected scenes, generated by the C++ input itself.
- manifest.json: version, assumptions and honest limits.

scripts/render_real_ccd_lab.py reads these files (not
a hand-authored movie) and generates five figures: 3D
mid-step impacts, near-miss geometry, candidate-to-event
reduction, all-pairs event coverage, and conservative
CCD fraction versus analytical time.

## Reproduce

    cmake -S . -B build-ipc -DCMAKE_BUILD_TYPE=Release \
      -DKYOTO_WITH_OFFICIAL_IPC=ON \
      -DIPC_TOOLKIT_WITH_SIMD=OFF
    cmake --build build-ipc --target kyoto_official_ipc_ccd_tests --parallel 4
    ctest --test-dir build-ipc -R pinned_official_ipc_continuous_CCD_coverage \
      --output-on-failure
    ./build-ipc/kyoto_official_ipc_ccd_tests results/ccd-gate
    python3 -m pip install numpy matplotlib
    python3 scripts/render_real_ccd_lab.py \
      --input results/ccd-gate \
      --output results/ccd-gate/visuals
